# 截断实验室 · Price × Censoring Lab

一个**虚构数据**的共享库存价格实验回放台。同一批耳机在四个渠道同时售卖，调价会改变需求，缺货又会截断观察——于是"卖得少"既可能是价格问题，也可能是没货可卖。这个应用把这件事做成可推演、可逐单追溯的本地沙盘。

> **不连接任何真实系统。** 所有曝光、订单、库存、支付与退货都是本进程用固定种子生成的虚构事件。应用不发起任何外部请求，不写数据库，不调用真实销售/库存/支付接口。

---

## 运行

需要 Node.js ≥ 20（开发与验证使用 v24）。**零运行时依赖**，不需要安装任何东西。

```bash
npm start          # http://127.0.0.1:4173
npm run dev        # 同上，node --watch
npm test           # node:test，27 个用例，约 1 秒
```

端口可用环境变量覆盖：`PORT=5000 HOST=0.0.0.0 npm start`（默认只监听回环地址）。

## 五个页面

| 页面 | 作用 |
| --- | --- |
| **回放台** | 推进时钟（一步 / 一天 / 跑完）、看今日各渠道价格与成交、共享库存条与时序、逐条事件流、规则版本、检查点与撤销 |

## 核心模型

### 世界

- 一个 SKU（成本 ¥68，参考价 ¥129），四个渠道：Marketplace / 品牌官网 / 移动 App / 奥莱门店；流量、基础转化率、价格敏感度、履约费各不相同。
- 28 天 × 每天 6 个时段 = 168 个 tick。四种需求情景：平稳、促销脉冲、连续升温、波动周。
- 种子固定（默认 `aurora-11`）→ 相同操作序列产生**完全相同**的回放；`toJSON`/`fromJSON` 可无损续跑。

### 两层库存预留

下单先占一个**软预留**（有 TTL），支付成功后转为**已承诺**。取消、超时、退货都会把件数还回可售池。不变量：

```
可用 + 预留中 + 已承诺 = 期初 + 补货
```

每个 tick 校验（`inventory.checkInvariant()`），并在 `/api/state` 里返回。库存事件与订单事件共用同一条带单调 `seq` 的事件流。

### 截断（censoring）

某渠道在某个 tick 卖空后，该时段的观察量只是"至少卖了这么多"，不是完整需求。所以：

- 事件里**从不记录**丢失的需求量；`exposure` / `stockout` 事件只记录发生过的成交。
- 分析时把该时段当作**右截断二项观测**，用 `P(Y ≥ y)` 而不是 `P(Y = y)` 进入似然。
- 页面同时提供「截断似然 / 剔除 / 当作完整（错误）」三种处理，用来直观看到 naive 做法会把缺货误判成"价格太贵"。
- 如果时段**开始时就已无货**，它不携带任何需求信息，直接被排除（`startedEmpty`）。

### 两种估计方法

- **按渠道独立**：每渠道一组 `(截距, 斜率)`，互不借用信息。简单，但忽略了"渠道间共享同一个库存池"造成的资源干扰。
- **联合（共享库存）**：加入共享交叉价格项 γ（其他渠道价格对本渠道转化的影响）。当各渠道价格同向变动时 γ 与自身价格共线、无法识别——此时模型**明确退化**为渠道固定效应（γ=0），并在界面与返回值里标明 `gammaDropped` / `gammaNote`，而不是悄悄给出一个看似显著的 γ。

识别诊断会逐渠道给出「可估计 / 弱识别 / 不可识别」以及原因（价格层级不足、未截断样本过少、价格与时间高度共线、弹性 95% 区间跨 0 等）。

### As-of 回测

每个收盘日只用**当天收盘前可见的**事件（`seq` 截止）拟合，去预测次日转化率，再与次日实际值比较。被截断的次日样本不计入误差；从来就空货的时段直接跳过。这样回测不会偷看未来。

### 方案生命周期与资源占用

`draft → confirmed → active → superseded`

- 草稿可任意改价；每次修改递增 `revision`。
- **确认**前必须通过规则核对（价格上下限、最大折扣、最低净贡献）、库存核减（预留 + 缓冲 ≥ 40 件），并记录**规则版本快照**与**库存快照**。
- 确认时携带 `expectedPrices` / `expectedRevision`：界面用旧价格发确认会被拒绝，防止"看到的和确认的不是同一版"。
- 所有方案共用**同一个可承诺库存池**，确认时按件预留；多个方案合计不能超过可承诺库存，旧方案不会因为新方案出现而多占。
- 规则 epoch 升级（平台费 +¥2、折扣上限 28% → 24%）会**释放**所有已确认方案的预留并标记 `rulesStale`，必须重新确认才能上线。
- 上线一个方案会把当前方案标记为 `superseded`；被取代的方案**不能再次上线**，再次点击会给出拒绝原因。
- 情景试算在**克隆引擎**上推演，不写事件、不动实时回放；并列比较会检查重复价格与预留合计是否超占。

## 架构

```
src/
  world.js      静态世界：SKU、渠道、情景、时钟常量
  rng.js        确定性 PRNG（种子 + 标签派生）
  inventory.js  软预留 / 承诺 / 释放 / 退货 + 不变量
  events.js     事件工厂（刻意不记录丢失需求）
  demand.js     潜在需求（logit + 渠道敏感度 + 稀缺抑制）
  engine.js     回放引擎：tick、订单结算、方案应用、序列化
  plans.js      方案状态机、规则快照、校验、预留核算
  rules.js      规则 epoch 与每渠道 ruleVersion
  stats.js      二项尾概率、Nelder–Mead、数值 Hessian、矩阵求逆
  analysis.js   行构建、截断似然、按渠道/联合拟合、识别、回测
  simulate.js   克隆引擎上的情景试算与并列比较
  session.js    操作意图层：撤销、检查点、方案流程、缓存、面向 UI 的状态
  server.js     零依赖 HTTP：静态文件 + JSON API
public/
  index.html    应用外壳
  styles.css    暗色设计系统
  js/           util / charts / store / dialog / nav / app + views/
test/
  engine.test.js  回放、库存、似然、识别、方案、撤销、序列化
  http.test.js    走真实服务器的请求体与接口回归
```

**数据流**：浏览器只持有一个 `state` 对象（最后一次服务端响应的副本），所有操作走 `POST/PATCH` 并替换该对象；视图是纯渲染函数，通过 store 订阅重绘。服务端是单用户、进程内的单个 `LabSession`，无数据库、无文件写入。

## 一次典型操作

1. 回放台点「推进一天」× 3，让各渠道积累一些未截断的曝光。
2. 方案实验室「新建草稿」，把某个渠道的滑杆下调——页面实时显示相对锚点的涨跌与净贡献。
3. 看「确认前核对」：改动未被确认的草稿、净贡献过薄、预留超过可承诺库存，都会在这里成为阻断或警告。
4. 「运行试算」比较"维持现价"与"该草稿"，注意试算页脚的说明：这是情景投影，不是实验结果。
5. 确认（勾选已知悉）→ 上线。旧方案自动变为 `superseded`，其预留被释放。
6. 再推进 5 天，回「结果与识别」：价格轨迹出现阶梯，识别诊断从「不可识别」变为「可估计 / 弱识别」，弹性区间与回测表格随之更新。
7. 「逐单日志」里找一笔下单时库存很低的订单，点开看它的预留是否被释放、为什么取消。低销量在这里通常有具体原因。

想制造库存竞争：把 `openingUnits` 调小、或用「补货」反向操作、或切换需求情景，然后比较靠前渠道与靠后渠道的成交差异。

## 测试覆盖

`npm test` 覆盖：

- 库存不变量（预留/取消/退货/补货）与"每个释放都对应一次预留"
- 缺货截断不破坏不变量，事件日志中不存在潜在需求
- 同种子确定性、存档往返后继续运行一致
- 渠道处理顺序如何改变谁拿到稀缺库存
- 规则上下限、规则升级使已确认方案失效、被取代方案不能再次上线
- 多方案预留不能超过可承诺库存
- 截断似然与 naive 处理的差异、as-of 回测只看过去
- 数值稳定性（矩阵求逆、二项尾、Hessian）
- 撤销/检查点恢复的是**过去**而不是当前（导出必须是深拷贝）
- 待支付订单不泄露"未来会取消"的内部判定
- 分析在无截止点时不把窗口坍缩为 0 行
- 弹性区间跨 0 时不得报告为"可估计"
- 走真实 HTTP 服务器的请求体与接口回归

## 边界

- 数据是**虚构**的；"需求"由模型假设生成，不是测量值。
- 截断时段只能给出下界与模型区间，缺口数字是推出来的，不能当事实。
- 一个共享库存池同时只能执行一个价格方案；并列比较是菜单选择，不是可同时投放的组合。
- 情景试算使用与回放相同的需求模型，因此它会"验证"模型本身，**不能替代真实实验**。
- 应用是单用户、单进程的内存回放；没有鉴权、持久化或多租户设计。
